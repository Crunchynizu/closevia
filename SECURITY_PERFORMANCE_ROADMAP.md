# Security and Performance Roadmap

This roadmap separates the remaining finalization work into two tracks: security and performance. It includes the batches already completed and the next batches to prepare before implementation.

## Completed Batches

### Security Batch 1: Client Package Cleanup

Status: Done.

- Removed unused vulnerable client export packages from `client/package.json`, including client-side Excel/PDF/DOC export libraries that were not imported from `client/src`.
- Kept admin CSV, JSON, and Excel export behavior because Excel files are generated by the backend and downloaded as blobs.
- Updated fixable frontend packages and refreshed the client lockfile.
- Verified the client production audit target with `npm audit --omit=dev`.

### Performance Batch 1: Frontend Performance Foundation

Status: Done.

- Fixed stale SPA shell caching while preserving long-lived hashed asset caching.
- Split the large Vite vendor bundle into targeted chunks.
- Removed saved-product request fanout from product listing/profile/detail surfaces by using `is_saved` data from product responses.
- Added responsive Cloudinary image attributes through the existing optimized image path.

### Performance Batch 2: Route and Page Load Responsiveness

Status: Done.

- Lazy-loaded heavier frontend routes to reduce initial page cost.
- Improved auth/session restore behavior so cached users can render faster.
- Allowed profile user data to render before slower product sections finish loading.
- Reduced rider polling pressure and avoided unnecessary polling while the page is hidden.

## Security Track

### Security Batch 2: Production Repository and Secret Hygiene

Status: In progress.

Goal: prepare the finalization branch so it does not ship local files, generated artifacts, stale dependencies, or accidental secrets.

Implementation scope:

- Remove tracked local/runtime artifacts from Git, including binaries, APK/AAB build outputs, logs, local databases, generated temp outputs, test uploads, `uploads/`, and `private_uploads/`.
- Keep only sanitized environment templates in Git. Remove local env backups and machine-specific env files from tracking.
- Update ignore rules so generated artifacts and local files do not return after future builds or tests.
- Consolidate old markdown summaries into a small final documentation set, instead of keeping many one-off implementation notes in the root.
- Clean or remove stale root npm dependencies if the root `package.json` is not part of the active frontend build. The active frontend dependency source should remain `client/package.json`.
- Recheck production secrets and deployment config:
  - `JWT_SECRET` must be strong and production-only.
  - DB credentials must only live in deployment/local env files.
  - Xendit secret keys and webhook tokens must only live in deployment env vars.
  - Firebase public config should be intentional, but private service credentials must not be committed.
  - CORS origins should be exact production/local origins, not broad wildcards.
- Verify debug/demo-only behavior is disabled or strictly gated in production.

Current cleanup pass:

- `.gitignore` has been tightened for local envs, build outputs, binaries, logs, reports, uploads, private uploads, local DBs, and stale root npm files.
- Generated/mobile build outputs, root package files, runtime uploads, logs, temp files, local DB files, and env backups have been removed from Git tracking while staying available locally where present.
- Mobile dependency audit was reduced from critical/high findings to remaining moderate Expo-chain findings with non-force fixes only.
- Documentation consolidation and production debug/demo review remain separate follow-up steps in this batch.

Success criteria:

- `git ls-files` no longer shows generated binaries, build artifacts, local DBs, logs, uploaded user files, private uploads, or local env backups.
- The finalization branch has one clear env template and no committed real secrets.
- Root dependency files are either cleaned or documented as intentionally unused.
- Security-sensitive deployment values are configured outside Git.

## Performance Track

### Performance Batch 3: Trade Fetching, API Fanout, and App Fetch Audit

Goal: reduce slow data fetching in trade-heavy pages and check whether the mobile/app side repeats the same slow patterns.

Implementation scope:

- Profile the web trade pages before changing code:
  - Identify which pages call `/api/trades`, `/api/trades/:id`, `/api/trades/loops`, `/api/trades/user/loops`, trade messages, delivery details, and payment/sync endpoints.
  - Check whether the UI fetches the same trade data multiple times after navigation, refresh, tab changes, or status filters.
  - Confirm whether proposed trade data is slow because of backend query cost, frontend duplicate calls, large payloads, or sequential dependent requests.
- Optimize trade list and proposed-trade fetching:
  - Add or improve pagination/limit behavior where a full trade history is loaded but only a subset is shown.
  - Avoid duplicate fetches across parent and child components by centralizing trade query ownership per page.
  - Cache trade lists and trade detail responses with sensible stale times in the frontend where data does not need second-by-second freshness.
  - Keep mutations invalidating only the affected trade/detail/list queries instead of forcing broad refetches.
- Review backend trade queries:
  - Check slow joins and repeated product/user lookups in `trade_handler.go`.
  - Add or confirm database indexes for common trade filters: buyer, seller, status, parent trade, loop/group identifiers, updated time, and product references.
  - Prefer list endpoints that return enough summary data for cards/tables so the frontend does not need one detail request per row.
- Check the mobile/app side too:
  - Review `mobile/shared/services/tradeService.ts` and screens that consume it for duplicate list/detail/message fetching.
  - Replace hardcoded production API assumptions with an environment-driven base URL if local testing or staging needs it.
  - Align mobile trade fetching with the web improvements so the app does not keep slower patterns after the web is fixed.
  - Audit mobile dependencies separately from the web client because `mobile/package.json` has its own dependency graph.

Success criteria:

- Proposed trade and trade list screens do not issue duplicate fetches for the same data during normal navigation.
- Trade list pages can load summaries without fetching every trade detail individually.
- Slow backend trade queries have supporting indexes or a documented reason they cannot be optimized yet.
- Web and mobile/app trade services follow the same API shape where practical.
- The app side has a clear local/staging/production API base URL story.

## Verification Plan

- Security:
  - `git status --short`
  - `git ls-files` artifact scan
  - `npm audit --omit=dev` in `client`
  - `npm audit --omit=dev` in `mobile`
  - `go test ./...`
- Performance:
  - `npm run build` in `client`
  - Browser network trace for dashboard, profile, trade list, proposed trade, product detail, rider pages, and admin dashboard.
  - Mobile/app network trace or console logging for trade list, trade detail, proposed trade, and messages.
  - Backend timing logs or query inspection for slow trade endpoints.

## Implementation Order

1. Implement Security Batch 2 first so the finalization branch is clean before more feature/performance edits.
2. Implement Performance Batch 3 after the cleanup, starting with measurement of trade and mobile/app fetch behavior.
3. Run full verification before merging the finalization branch.
